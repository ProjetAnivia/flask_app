🗄 Données & API
ProtectionDétailÉtat
Requêtes SQL paramétrées 100% des requêtes SQL utilisent des placeholders SQLite (?), aucune concaténation de chaînes → immunisé contre l'injection SQL. actif
Validation des entrées Chaque endpoint valide types, bornes, formats (regex pour dates/heures, min/max pour numériques, longueurs pour textes). Erreur 400 explicite si invalide. actif
Escape HTML automatique (Jinja) Tous les outputs Jinja sont auto-escapés. Protection contre XSS stocké. Filtre | safe jamais utilisé sur des inputs utilisateur. actif
Secrets (Google Calendar, etc.) Stockés dans secrets/ avec permissions 600, git-ignored. Jamais loggés. actif
📋 Recommandations à présenter au client
  • 2FA obligatoire pour les admins : on a la fonctionnalité, on peut rendre l'activation obligatoire au prochain login pour le rôle admin.
  • HTTPS en prod : dès que le Dashboard est exposé hors localhost, activer HTTPS_ENABLED=true + certificat (Let's Encrypt si Internet, certif interne sinon). Active automatiquement Secure sur les cookies.
  • Rotation des credentials Google Calendar : la clé service-account actuelle a transité par chat — à révoquer et regénérer dans la console GCP avant mise en production.
  • Backups DB : le script backup.sh existe ; à brancher sur un cron (1×/jour conseillé) avec rétention de 30 jours.
  • SECRET_KEY : définir une valeur aléatoire forte (python -c "import secrets; print(secrets.token_hex(32))") dans la variable d'environnement avant le déploiement.
